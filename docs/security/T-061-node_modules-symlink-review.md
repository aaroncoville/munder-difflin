# Security review — T-061: symlink `node_modules` into isolated worktrees

**Reviewer:** Creed (adversarial security auditor, worker-t061-sec)
**Date:** 2026-08-24
**Under review:** branch `agent/worker-t061-qa` @ `2ea95a88`
**Change:** new `src/main/worktreeDeps.ts` (`linkWorktreeDeps`), called from `spawnAgentCore`
(`src/main/index.ts:2682`). At spawn, an isolated worktree gets `<worktree>/node_modules` created as an
**absolute symlink** to `<base checkout>/node_modules`.

## Recommendation (one, not a menu)

**SHIP AS-IS.**

The thesis under attack — *"this deliberately punches a hole in worktree isolation and creates a new
cross-agent code-execution path"* — **does not hold**. The write path into the base `node_modules` already
exists for every worker, is reachable without the symlink, and depends on nothing this commit introduced. The
symlink is a convenience alias over an **already-permeable boundary**. It adds no new write capability and no
new blast radius. One genuinely new effect is a *reliability* footgun (accidental `npm install` in a worktree
now corrupts the shared base install) — LOW severity, already mitigated by the warning added in the same
commit, and optionally hardenable. It is not a security-boundary regression.

## Why the boundary was never an OS boundary (the crux)

Worktree "isolation" in this app is a **git working-tree / branch** separation, not an OS sandbox. Workers run
as full-access processes:

- Auto-mode flags (`src/shared/agentProvider.ts`):
  - claude / grok: `--permission-mode bypassPermissions` (lines 173, 261)
  - codex: `--dangerously-bypass-approvals-and-sandbox` (line 207) — the preset comment states plainly:
    *"drop the sandbox … full-access posture … The app already runs claude/agy in this same full-access
    posture."*
  - agy: `--dangerously-skip-permissions` (line 320)
- No OS sandbox wrapper: grep for `sandbox-exec|seatbelt|firejail|bwrap|nsjail` across `src/main/**` = **0
  hits**. Workers exec directly under node-pty as the same OS user (Aaron).
- No filesystem deny-list confines writes: no project `settings.json` permissions block; `~/.claude` carries
  no `deny` / `additionalDirectories` rules — and `bypassPermissions` ignores those anyway.

**Consequence:** every worker can already write to any absolute path the OS user can write, including
`/Users/aaroncoville/code/munder-difflin/node_modules`.

The base checkout is trivially discoverable from inside any worktree, with a standard git command, requiring
neither the symlink nor the new `[ENVIRONMENT]` note:

```
$ git -C <any worktree> rev-parse --git-common-dir
/Users/aaroncoville/code/munder-difflin/.git      # base = dirname of this
```

So this one-liner was reachable **before** the commit and remains the true capability:

```sh
echo 'evil' > "$(dirname "$(git rev-parse --git-common-dir)")/node_modules/.bin/tsc"
```

The symlink merely lets the same worker instead write `./node_modules/.bin/tsc` — **same inode target, same
effect, same pre-existing reachability.**

## The five questions, answered with evidence

### Q1 — Can a worker write through the symlink into the base `node_modules`?

**YES.** A symlink to a directory is transparent for writes. Demonstrated safely in scratchpad (no real
`node_modules` touched):

```
base/node_modules/.bin/tsc  == "ORIGINAL"
ln -s base/node_modules  wt/node_modules          # reproduces linkWorktreeDeps
echo "PWNED-by-worker" > wt/node_modules/.bin/tsc # write THROUGH the worktree path
cat base/node_modules/.bin/tsc  -> "PWNED-by-worker"   # base overwritten
echo "malware" > wt/node_modules/.bin/evil.sh          # NEW file also lands in base
ls base/node_modules/.bin/  -> evil.sh  tsc
```

Both overwrite and new-file drop pass straight through.

### Q2 — Blast radius: does the running app / next worker's typecheck pick up a modified `.bin` shim or package `main`?

**YES, but this blast radius pre-existed the symlink.** There is a single `node_modules` (base) shared by:
Aaron's dev build (`npm run dev` runs from base), Aaron's manual `npm run typecheck` / `node --test`, and every
worktree worker (a worker's `npm run typecheck` resolves `node_modules/.bin/tsc` and package requires from cwd
upward → the worktree symlink → base). Poisoning base `node_modules` therefore executes attacker code in all of
them on their next run.

Crucially, the change does **not** create this shared surface. Base `node_modules` was always one shared,
writable directory reachable by any worker (Q3/crux). The symlink adds a second *name* for the same target, not
a new target. Net new blast radius from the commit: **none.**

### Q3 — Is there a sandbox/permission layer that already prevents this, or does the harness rely on worker good behaviour?

**No preventive layer; the harness relies on worker good behaviour.** As shown in the crux section: workers run
with `bypassPermissions` / `--dangerously-bypass-approvals-and-sandbox`, no OS sandbox wrapper, no FS deny
rules, same OS user. The permission model here is *"skip all prompts"*, not *"confine the filesystem."* This is
a deliberate, pre-existing property of the floor (the app runs every provider in this full-access posture), not
something the symlink weakens.

### Q4 — Is silently skipping a pre-existing `node_modules` entry safe? Can a worker plant a symlink pointing elsewhere?

**Safe in practice; the "points elsewhere, planted by an attacker" scenario is unreachable at that point in the
lifecycle.**

- Ordering: `linkWorktreeDeps` runs **inside `spawnAgentCore`, immediately after `git worktree add` and before
  the worker process is launched** (`index.ts:2673→2682`). `git worktree add` creates a fresh working tree with
  **no** `node_modules`, so `lstat` normally fails → the symlink is created. At that instant **no worker exists
  yet** to have planted anything, so an attacker-controlled pre-existing link cannot be present.
- `wtPath` is deterministic per agent id (`join(wtRoot, slug(id))`, `index.ts:2666`) and the id is slugified
  with a `..`/separator guard and an under-root assertion (`index.ts:2666–2669`) — good existing defense against
  path injection. A live duplicate id makes `addWorktree` conflict and fall back to base cwd (no link). So two
  concurrent spawns cannot race on the same `wtPath`, and the swallowed `EEXIST` (`.catch` at `index.ts:2682`,
  and the `try/catch` returning `{ok:false}` in `worktreeDeps.ts`) has no realistic trigger. When it does fire
  it is non-fatal by design — it leaves whatever entry already won and logs.
- If a stale/bad link ever *were* skipped (e.g. hypothetical worktree-path reuse where teardown failed to
  clean — `git worktree remove --force` does clean the dir), the only victim is **that worker's own** typecheck
  resolving to the wrong deps. That worker already runs arbitrary code; it is self-harm, not cross-agent
  escalation.

**Optional hardening (not required to ship):** instead of skipping on *any* pre-existing entry, resolve it and
skip only when it already points at `<base>/node_modules`; otherwise refuse (and log) rather than trust an
unexpected link. Cheap defense-in-depth against the theoretical reuse case.

### Q5 — The symlink target is absolute. Consequences if the base path is attacker-influenced or later moved?

- **Base moved:** the absolute link dangles → worktree typecheck fails with the "missing toolchain" symptom the
  change exists to prevent. Benign; the `[ENVIRONMENT]` note tells the worker to fall back to running from the
  base checkout or ask god to restore it.
- **Attacker-influenced base:** `origCwd` = `opts.cwd` = `raw.cwd` of the spawn request, gated by
  `existsSync` (`index.ts:4691` region). A crafted `cwd` would point the link (and the worker's whole run) at an
  attacker-chosen tree — but that is the **pre-existing spawn-request attack surface** (a spawn-request is not
  human consent), and its blast radius is the worker attacking itself with attacker-chosen deps. The symlink
  neither creates nor widens it. Out of scope for this commit; flagged for completeness.

## One genuinely new — but LOW, non-security — footgun

Before this commit a worktree had **no** `node_modules`, so an accidental `npm install` / `npm ci` there built a
**local, isolated** install (harmless to base). After it, `node_modules` is a symlink, so `npm install` in the
worktree **writes through / replaces the link and mutates the shared base install mid-flight**, corrupting every
concurrent worker and Aaron's dev build. This is a **reliability** regression, not a new security boundary
breach (a worker could already corrupt base deliberately). It is already mitigated by the explicit
`[ENVIRONMENT]` warning added in the same commit ("DO NOT run `npm install`…"). Severity: **LOW.**

## Escalation

Nothing HIGH. No new code-execution path. Not routed to the human.
